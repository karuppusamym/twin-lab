# Factory playbook: building a demo app from a brief

For an AI coding agent (Devin, Copilot agent, Claude Code, Cursor) building one demo app in Twin
Lab. The short form is [`AGENTS.md`](../AGENTS.md). Adapted from Application Twin Studio's
playbook: the trust rules are the same, the thing being built is different.

## What you are building

A copy of a real application, in the same framework and versions, that does what the registered
automations need from it and nothing else. The brief at `apps/<app>/BRIEF.md` defines "what they
need". The real application's source, named in the brief, defines "how it looks and behaves".

```
apps/<app>/BRIEF.md + the source files it names
        │
        ▼
 you ──► apps/<app>/ (frontend, backend, Dockerfile) ──► pull request
                                                          │
          CI: build image · run it · conformance · tests ◄┘
          a person reviews: the brief's reviewer, and the app owner for rules
```

## Inputs and outputs

| You read | You write |
|---|---|
| `apps/<app>/BRIEF.md` | Everything under `apps/<app>/` except the files in the next row |
| The source files the brief lists, and only what they import | `apps/<app>/BUILD-NOTES.md`: what you did, what you could not do, and why |
| `apps/<app>/db/schema.sql`, `db/seed.sql` | |
| `apps/<app>/pages/*.html`: one snapshot per recorded screen | |
| `apps/<app>/navigation.json`: every way from screen to screen, dialogs, tabs, frames, popup windows, and every element of each screen with what it did | |
| `apps/<app>/codemap.json`: what the application's code defines: every route (recorded or only in code), guards, lazy chunks, menus, tabs, dialogs, API calls (called or not), interface texts, lists of values | |
| `apps/<app>/api/catalogue.json` and `api/*.json`: every endpoint the pages called, with schemas and synthetic calls | |
| `apps/<app>/rules.json`: per screen and field, every validation rule with its message and level, rules between fields, behaviour while typing or choosing, state on load, session timers | |
| `apps/<app>/steps/*.json`, `*.values.yaml`: the recorded steps and the values the acceptance replay types | |
| `apps/<app>/app.yaml` | Only its `run:` section |
| `apps/<app>/pages/*.html` and `apps/<app>/look/` (when there is no source): value-free snapshots of each screen, the original style sheets, `theme.json`, a picture per screen, the interface's images, `texts.json` | |

You do not change: `BRIEF.md`, `db/schema.sql`, `app.yaml` outside `run:`, anything outside
`apps/<app>/`. If the brief is wrong, say so in `BUILD-NOTES.md`; the brief is regenerated by a
person, not edited by you.

## How to build

1. **Same stack, same versions.** Use the exact frontend versions in "Stack to pin". Where the
   brief gives a range for the backend, pin to the newest version in that range and say which,
   unless the brief names the version the real application runs.
2. **Same selectors.** Every element in the brief's screen tables keeps its tag, id and classes.
   Keep the rest of the screen's markup as close to the source as you can: automations rely on
   structure they do not name.
3. **Same behaviour on the in-scope paths.** Read the screen files and route handlers the brief
   lists. Reproduce what they do: conditional fields, cascades, disabled states, messages, status
   codes, error bodies. Copying in-scope source code is allowed and usually the most faithful
   approach; then remove everything out of scope. Every field a route lists as *automations
   read* (taken from the bots' own code, for example `token` or `items[].review_no`) is in its
   success answer under exactly that name, and every field it lists as *automations send* is
   accepted. A bot breaks on a missing one even when conformance is READY.
   **Same rules.** Every rule of `apps/<app>/rules.json` (the brief's *Field rules and page
   behaviour*) at level `seen` or `declared` is implemented exactly, with its message letter
   for letter; a rule `in code, not triggered` is implemented too, since the real application
   has it; a rule `in code, not tied to a field` where the brief places it, with your choice in
   `BUILD-NOTES.md`. The same holds for the masks, the fields shown or enabled by another, the
   drop-downs filled from the API, a submit button disabled until the form is valid, the state
   on load and the session timers listed there.
   **Same look.** When the brief has a *Look and feel* section, start from the style sheets in
   `apps/<app>/look/css/`, check against `look/theme.json`, and compare each screen with its
   picture in `look/screens/`. Literal texts (`look/texts.json`) are copied exactly; a
   placeholder (`Xxxx`, `9999`) stands for data and is never shown. Fonts the package does not
   hold are obtained under their licence or replaced by the fallback `look/manifest.json`
   names. Copy what you use out of `look/`; leave the folder as it is.
4. **Nothing out of scope.** No screen, route, table, menu link or model listed under "Out of
   scope". A link a recorded page already has to an out-of-scope path stays as the snapshot has
   it and is answered with a redirect to the first in-scope screen, as the brief's *Navigation
   map* says for each one.
5. **Database from `db/schema.sql`.** Table and column names exactly as there, on the engine the
   brief names. The database is a server outside the container (the lab slows it down through a
   proxy), so include its driver and read its address from the environment variable the brief
   names. Create the tables from `db/schema.sql` when the database has none (the lab may already
   have created them). The engine can be Postgres, SQL Server or Oracle; the lab also sets
   `DB_ENGINE`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_SERVICE`, `DB_USER`, `DB_PASSWORD` and
   `DB_CONNECTION_STRING` (ADO.NET), so a .NET app reads its connection string as it is.
   A **view** in the schema is a **table** of that name in the demo database: read and write it as
   a table and never re-create its query. Stored procedures, functions and triggers are not in the
   demo database; if an in-scope path calls one, write its effect in the app and say so in
   `BUILD-NOTES.md`.
   **Enhancing an app that already exists** (its `Dockerfile` is on main): change only what the
   new brief adds or changes, keep every existing selector, route and field, and say in
   `BUILD-NOTES.md` what changed and why.
6. **Health route** at the path the brief states. It answers 200 only when the database is
   reachable, because the lab uses it to tell a broken app from a slow one.
7. **One container.** One `Dockerfile` in `apps/<app>/` that builds the front end and serves it
   and the API from one process on one port. Multi-stage builds are fine. No lab code in the
   image. No secrets in the image.
8. **Data.** No real data. The source's seed may be kept so the app is usable on its own; mark it
   clearly as synthetic. Test credentials stay in the seed file only.
9. **Fill `app.yaml` `run:`** with the container port for `web` and `api` (the same port if one
   process serves both) and the health path.

## What a build package holds

`labctl builder package` (and `labctl evidence build-all`) writes one zip per application. Its
`INDEX.md` lists every file with one line on what it is for, and `BUILD_TASK.md` gives the order
to read them in:

| File | What it is |
|---|---|
| `BUILD_TASK.md`, `INDEX.md`, `MANIFEST.json` | The task, the list of files, their checksums and the result of the completeness check |
| `apps/<app>/spec/CONSTITUTION.md` | The rules that are not negotiable (the task's own text) and what "done" means |
| `apps/<app>/spec/ARCHITECTURE.md` | Stack, layers, route table, API surface, data model, sign-in, session and cookies, how the app runs |
| `apps/<app>/spec/BUILD-PLAN.md` | The build in order, each step with its "done when" lines |
| `apps/<app>/spec/PAGES/<NN>-<screen>.md` | One per screen: everything that screen needs, each fact with its file; pages not recorded and screens known only from code are marked |
| `apps/<app>/spec/GLOSSARY.md` | Option lists, code lists, statuses, the package's words |
| `apps/<app>/BRIEF.md` | The full specification, the reference behind `spec/` |
| `apps/<app>/session.json` | Sign-in and session as recorded; every cookie by name with its attributes, never a value |
| `apps/<app>/pages/` | One snapshot per screen: structure and interface text real, data masked |
| `apps/<app>/look/` | Style sheets, theme and a picture per screen, when that step has run |
| `apps/<app>/navigation.json` | The navigation map and the actions of each screen; each transition says its source (`recording`, `page`, `code`) |
| `apps/<app>/codemap.json` | What the application's code defines. Build every route in it at least as a reachable page with its menus, tabs and dialogs wired as listed; a recorded screen follows its snapshot; a screen only the code has is built from its route, title, menu text and API calls, and listed in `BUILD-NOTES.md` under *Reconstructed from code* |
| `apps/<app>/api/` | The API catalogue: one file per endpoint, synthetic examples only |
| `apps/<app>/rules.json` | Field rules and page behaviour, each with its level and evidence |
| `apps/<app>/scripts/` | Only with `TWINLAB_PAGE_SCRIPTS=carry`: the application's own scripts, checked |
| `apps/<app>/db/` | `schema.sql`, and `seed.sql` / `seed.json` with the rows to load at start (the replay's user in `app_users`) |
| `apps/<app>/steps/` | The recorded steps, the replay values, the order across applications |
| `apps/<app>/model.yaml`, `behaviours.json`, `app.yaml` | Reference |

The packaging step checks that every screen has an actions list and a page file, every endpoint
a schema, every navigation target a definition, every table seed rows and every typing step a
value. What it finds is written into the task and the index and printed as a warning; with
`TWINLAB_PACKAGE_STRICT=1` the package is refused instead.

Read the package in this order: `BUILD_TASK.md`, `spec/CONSTITUTION.md`, `spec/ARCHITECTURE.md`,
`spec/BUILD-PLAN.md`, then the page files one by one as you build each screen. The brief and
the machine files are the references the documents point to. The documents are generated from
the package and never edited; a cookie value is in none of them and is not needed (set each
cookie with its recorded name and attributes and a value of your own).

## Rules and trust

- Every rule in `app.yaml` stays `verification: hypothesis`. Never raise it.
- Do not invent behaviour the source does not have. If the brief's open questions leave something
  undecided, choose the simplest reading, and list it in `BUILD-NOTES.md` under "Assumptions".
- Do not change tests or checks to make them pass. Report failures as they are.
- Synthetic data only, in code, fixtures, logs and pull-request text.

## Before you say you are done

From the repository root:

```bash
docker build -t twinlab/<app>:dev apps/<app>
```

```bash
docker run --rm -p <host port>:<container port> twinlab/<app>:dev
```

Then, against the running container: the health route answers 200; each screen in the brief opens
and shows its listed selectors; each route in the brief answers on its method and path; each rule
in `app.yaml` behaves as written; nothing out of scope answers (expect 404). Put what you checked,
and how, in `BUILD-NOTES.md`. If you could not check something, say so there.

When `labctl conformance` exists (T-07), run it too:

```bash
labctl conformance <automation id>
```

## Pull request

Title `<app>: demo app from brief <digest>`. Body: the checks you ran with their results, the
assumptions list, and anything in the brief you think is wrong. One pull request per app.

## For the reviewer

Read `BUILD-NOTES.md` first. Then check, in order: nothing out of scope exists; the pinned versions
match; the rules behave as the brief says; the assumptions are acceptable. Record in the app's
`BUILD-LOG.md` how many rounds of correction it took and what was wrong in each, so the playbook
and the brief generator can be improved.
