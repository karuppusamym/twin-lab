# Loan Desk (demo copy) on OpenShift (apply by hand)

Generated by `labctl ocp render --manual`. Do not edit these files by hand: change the app or the options and render again, so the folder stays what `labctl ocp check` approved. Nothing here holds a password or token.

- **App:** `loandesk`, listening on port 8080; health path `/api/health`

- **OpenShift project:** `twinlab` (named inside every file; to use another, render again with `--namespace`)

- **Images:** built in the cluster from `https://github.com/karuppusamym/twin-lab.git`, branch/ref `main`

- **The lab here is:** ONE pod with an init step, the lab agent and the app sharing the SQLite file's volume (PVC); no database pod

## Before you start

- Someone with rights on the project (`edit`) and the `oc` command line, or the web console (**Import YAML**, the `+` at the top right).

- The project exists: `oc new-project twinlab` (a cluster administrator may have to).

- The project may run Docker-strategy builds (`oc auth can-i create builds/docker`; ask the administrator if it says `no`) and the cluster's internal image registry is on.

- The build pods can reach `https://github.com/karuppusamym/twin-lab.git` and the image sources the Dockerfiles use (`python:3.13-slim`), and the package registries `pip` (and `npm`, for apps with a front end) read. In an office that usually means a mirror: ask for the cluster's proxy or mirror settings (they are set cluster-wide, not in these files).

- The repository must be readable without a login. If it is private, render again with `--source-secret <name>` and create that secret (see the private repository note below).

- A default storage class that can make `ReadWriteOnce` volumes (or render again with `--storage-class <name>`, or `--ephemeral` to use no volumes at all).



## 1. Create the Secret by hand (once)

The Deployments read `twinlab-loandesk-secrets`; it is not in these files so no value is ever in Git. Make up the values (here they are random); keep them for whoever needs the admin API.

```bash
oc create secret generic twinlab-loandesk-secrets -n twinlab \
  --from-literal=lab-token="$(openssl rand -hex 24)"
oc label secret twinlab-loandesk-secrets -n twinlab app.kubernetes.io/part-of=twinlab app.kubernetes.io/instance=loandesk
```

Keys it needs: `lab-token`. In the console: **Workloads > Secrets > Create > Key/value secret**, one entry per key. Never create it again on a running lab: everyone using the admin API would need the new token.


### Private repository

The BuildConfigs name a source secret only when rendered with `--source-secret <name>` (this folder does not); the secret is yours to create:

```bash
oc create secret generic <name> -n twinlab --type=kubernetes.io/basic-auth \
  --from-literal=username=<git user> --from-literal=password=<access token>
```



## 2. Apply the files, in order

From this folder, as a user who can edit project `twinlab`:

```bash
oc apply -f . -n twinlab      # the numbered files apply in name order
# or: oc apply -k . -n twinlab
```

In the console, open **Import YAML** and paste the files one after another in number order (the page accepts several documents separated by `---`). Objects that need the Secret wait for it; they start when it exists.

## 3. Build the images

```bash
oc start-build twinlab-loandesk-agent -n twinlab --follow
oc start-build twinlab-loandesk-app -n twinlab --follow
oc get builds -n twinlab -l app.kubernetes.io/instance=loandesk
```

The first builds take several minutes. In the console: **Builds > BuildConfigs** > the build > **Start build**, then the **Logs** tab. When a build pushes its image, the Deployment that uses it rolls out by itself: its `image.openshift.io/triggers` annotation names the ImageStream tag (`latest`) to follow. (The annotation was chosen over a DeploymentConfig trigger, which is deprecated.) Start the builds again whenever the branch changes; nothing starts them for you. Until the first builds finish the pods show `ImagePullBackOff` or `Init:ImagePullBackOff`: that is expected.



## 4. Watch it come up

```bash
oc get pods -n twinlab -l app.kubernetes.io/instance=loandesk -w
oc logs deployment/twinlab-loandesk-lab -c agent -n twinlab
```

Everything is in the one pod of `twinlab-loandesk-lab`: its init container `sqlite-init` runs first (it makes the database file and the tables), then the `agent` and `app` containers. `oc logs deployment/twinlab-loandesk-lab -c app` shows the app.

## 5. Check health through the Route

```bash
HOST=$(oc get route twinlab-loandesk-web -n twinlab -o jsonpath='{.spec.host}')
TOKEN=$(oc get secret twinlab-loandesk-secrets -n twinlab -o jsonpath='{.data.lab-token}' | base64 -d)
curl -s -H "X-Lab-Token: $TOKEN" https://$HOST/_lab/health    # the lab agent: app up
curl -s -o /dev/null -w '%{http_code}\n' https://$HOST/api/health    # the app itself
```

No `curl`? Open `https://<route host>/api/health` in a browser (the host is on **Networking > Routes**); the app answers without the token. Add `-k` to `curl` if the router's certificate is self-signed. `401` from `/_lab/health` means the token is wrong; `503` means the agent runs but the app or database is not up yet.

## 6. Load data, take the baseline, reset

The lab agent's admin API (header `X-Lab-Token`) is what the portal uses locally:

```bash
# once the lab is healthy: record the starting data, so Reset has something to go back to
curl -s -X POST -H "X-Lab-Token: $TOKEN" -H "Content-Type: application/json" -d '{"label": "start"}' https://$HOST/_lab/data/baseline
# load rows ({"rows": {"<table>": [{...}, ...]}, "label": "..."}) from a file
curl -s -X POST -H "X-Lab-Token: $TOKEN" -H "Content-Type: application/json" --data @rows.json https://$HOST/_lab/data/load
# put the data back to the baseline
curl -s -X POST -H "X-Lab-Token: $TOKEN" https://$HOST/_lab/reset
# what the lab holds; conditions (slow pages) and sessions have their own paths
curl -s -H "X-Lab-Token: $TOKEN" https://$HOST/_lab/info
```

## 7. Roll back

Every build keeps its image in the ImageStream. Point `latest` at an older one and the Deployment follows:

```bash
oc describe imagestream twinlab-loandesk-app -n twinlab     # every pushed image, newest first
oc tag twinlab-loandesk-app@sha256:<older digest> twinlab-loandesk-app:latest -n twinlab
# the agent the same way: twinlab-loandesk-agent
```

For a quick undo of the last rollout: `oc rollout undo deployment/twinlab-loandesk-lab -n twinlab`. The next build moves `latest` forward again. The data stays on its volumes either way.

## 8. Remove everything

```bash
oc delete all,configmap,pvc,secret,job,networkpolicy,imagestream,buildconfig,route -n twinlab -l app.kubernetes.io/instance=loandesk
```

This also deletes the data (the volumes) and, if you labelled them as above, the Secrets. Check first with the same selector and `oc get` in place of `oc delete`.

## What differs from the local lab

- **One copy per app** in the project, shared by everyone who uses it: there are no copies per run (`labctl lab copy`), no per-run ports, and the portal does not manage it yet; use the admin API above.

- **Bots** reach the app through the Route (HTTPS). There is no database link: SQLite is a file inside the pod, so bots get no database address and database slowdowns (fault conditions) cannot apply; web conditions and sessions do.

- The SQLite file sits on a `ReadWriteOnce` volume mounted by one pod only, in WAL mode. A network file system that does not support shared-memory mapping can break WAL: use block storage.

- **Everything runs as an arbitrary user** the cluster picks (the `restricted-v2` security context constraint): no root, no extra capabilities. Nothing needs more.

- Nothing here was tried on a real cluster when it was generated: the first apply is the real test. `labctl ocp check <this folder>` verifies the files offline before you do.
