## Round 1 (2026-11-15)

**Built:** a two-stage Dockerfile (Node 20 builds the front end; Python 3.13 runs uvicorn as a
non-root user and serves the API and the built front end on port 8000), the in-scope backend
copied from the source with the canned-response model, routes and seed removed, the front end
copied unchanged apart from the out-of-scope route and nav link, and `app.yaml` `run:` filled.
Took about 10 minutes and 57 tool calls.

**Review:** 42 of 42 independent checks passed. The front-end files are byte-identical to the
source, apart from `main.tsx`, which differs only by the removed import, route and link. Nothing
out of scope remains in code; out-of-scope paths answer 404.

**What the agent got wrong:** nothing against the brief.

**What the brief and playbook got wrong** (raised by the agent, confirmed by the reviewer):

1. **The database could not be put behind the lab's proxy.** The brief carried the source's
   SQLite default, so the app kept its database inside the container. The lab needs a database
   server it can slow down (T-13), and the sample UiPath bot queries the database directly through
   a Postgres driver. Fixed in the generator: `labctl brief --db-engine`, and an open question
   whenever the source only shows SQLite.
2. **The schema had no identity columns.** On Postgres, inserting a note or an audit row without
   an id would have failed. Fixed: single-column integer keys are now generated per dialect
   (`GENERATED BY DEFAULT AS IDENTITY` on Postgres), tested on a real Postgres.
3. **The brief and the playbook disagreed on backend versions.** The brief said to pin the
   version the real application runs; the playbook said the newest in range. Aligned: newest in
   range, unless the reviewer names the real version.

Result: correction requested. The brief was regenerated with `--db-engine postgres`.

## Round 2 (2026-11-15)

**Asked:** run on a Postgres server through `DATABASE_URL`, with a pinned driver, identity
sequences that keep working after the seed's explicit ids, tables from the regenerated
`db/schema.sql`, a decision on what happens without `DATABASE_URL`, and verification on a real
Postgres. About 7 minutes and 31 tool calls.

**Built:** psycopg 3 added; the app waits up to 30 s for the database, creates the tables from
`db/schema.sql` when none exist, seeds once, and moves every identity sequence past the highest id
on each start. It refuses to start without a Postgres address. Its reason: a SQLite fallback
would need a second schema, and it would look healthy while the lab's proxy and the bot's direct
SQL reached nothing. The reviewer accepts this.

**Review on Postgres 17:** 42 of 42 independent checks passed. The bot's own query from
`Main.xaml` (the `case_audit` join on `cases`) runs on the demo database and returns the audit
trail the app wrote. The database holds exactly the 7 in-scope tables.

**What the agent got wrong:** nothing against the brief. It found and fixed something the brief
did not mention: the source's seed inserts `case_audit` before `cases`, which only works on a
database that does not enforce foreign keys. That is a property of the source app, so it stays in
the source; the copy's seed is ordered correctly.

**Open, for later items:**
- T-10 (data packs): loading rows with explicit ids must move the identity sequences, as the app
  does at start-up, or the next insert collides.
- T-13 (database proxy): the app has no connection timeout beyond the driver's default, so a
  proxy that holds connections may make health slow rather than failing. Check it there.
- The brief does not name a Postgres version; 17 is what was tested.

Result: **accepted after 2 rounds.** Round 1 was correct against its brief; round 2 corrected
the brief, not the agent's work. Both corrections led to changes in `labctl brief` and the
playbook, so the next app should not need them.
