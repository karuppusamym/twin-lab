## Round 2: Postgres

The brief was regenerated. The database is now a Postgres server outside the container, reached
through `DATABASE_URL`, and `db/schema.sql` is Postgres DDL with
`GENERATED BY DEFAULT AS IDENTITY` keys. The playbook's step 1 now agrees with the brief on
pinning backend versions (newest in range unless the reviewer names one). Nobody named one, so
the round 1 pins stay.

### What changed

| File | Change |
|---|---|
| `backend/requirements.txt` | Added the driver: `psycopg==3.3.9` and `psycopg-binary==3.3.9`, the newest psycopg 3 on 2026-11-15. |
| `backend/app/main.py` | `create_app` now needs a Postgres URL. `postgresql://`, `postgres://` and `postgresql+<driver>://` are all accepted and run on the psycopg driver. At start-up the app waits up to `DB_WAIT_SECONDS` (default 30) for the server. It then runs `db/schema.sql` unchanged when none of the 7 tables exist (the rule for a partial set is the same as round 1). It seeds when `app_user` is empty, then moves every identity sequence to `MAX(id) + 1` (`setval(pg_get_serial_sequence(...), ..., false)`). The engine uses `pool_pre_ping`, so the app recovers when the database comes back. The SQLite code (default URL, `check_same_thread`, `StaticPool`) is gone. |
| `backend/app/seed.py` | Same rows, but inserts are now ordered for foreign keys: the session is flushed after each category, before its sub-categories, and audit rows and notes are added after the cases are flushed. Postgres checks foreign keys and SQLite (as the source uses it) does not. The source models have no relationships between these tables, so SQLAlchemy inserted `case_audit` before `cases`, and the first run on Postgres failed with `ForeignKeyViolation`. The random number sequence and the ids per table are unchanged. |
| `Dockerfile` | `/app/data` is gone. The comment says `DATABASE_URL` is required. The health check's start period went from 10 s to 40 s to cover the database wait. |
| `app.yaml` | No change: `run:` was already right (port 8000, `/api/health`, `DATABASE_URL`). A person set `stack.db.engine: postgres`. |

### When `DATABASE_URL` is not set: refuse to start

The app stops at start-up with `RuntimeError: DATABASE_URL is not set. ...`. A non-Postgres URL
also stops it, for example `sqlite://...` gives `DATABASE_URL must be a postgresql:// URL, not
sqlite://`. Why:

- `db/schema.sql` is Postgres DDL (`GENERATED BY DEFAULT AS IDENTITY`). A SQLite fallback could
  not apply it unchanged, so it would need a second schema or `create_all` from the models. Both
  break the "tables from `db/schema.sql`, unchanged" rule, and its tables could drift from the
  real ones.
- The lab must reach the database through its proxy. A silent fallback to a database inside the
  container would hide a missing or mistyped address: the app would look healthy while the
  proxy, the slowdowns and the automation's direct database reads all went nowhere.
- Failing at start-up shows up at once and says what to set.

Cost: there is no zero-configuration local run. Use a Postgres container, as in the commands
below.

### How to run (round 2)

From the repository root:

```bash
docker build -t twinlab/showcase:dev apps/showcase
docker network create showcase-net
docker run -d --name showcase-pg --network showcase-net -e POSTGRES_USER=showcase -e POSTGRES_PASSWORD=showcase-local -e POSTGRES_DB=showcase postgres:17-alpine
docker run -d --name showcase-dev --network showcase-net -p 8720:8000 -e DATABASE_URL=postgresql://showcase:showcase-local@showcase-pg:5432/showcase twinlab/showcase:dev
```

The Postgres user and password are local test values passed at run time. Nothing is baked into
the image. Postgres is not published on a host port; reach it with
`docker exec showcase-pg psql -U showcase -d showcase`.

### Assumptions (round 2)

1. The app refuses to start without a Postgres `DATABASE_URL` (reasons above).
2. Any `postgresql://` or `postgres://` URL runs on psycopg 3, the only driver in the image.
3. Start-up waits up to 30 s (`DB_WAIT_SECONDS`) for the database, then exits. The source has no
   such wait. It was added because in the lab the database is a separate container behind a
   proxy and may start later.
4. Identity sequences are re-synced to `MAX(id) + 1` on every start, not only after seeding, so
   that rows loaded with explicit ids (for example by data packs) between restarts are also
   covered. Rows loaded while the app is running are not covered until the next start.
5. There is no connection timeout beyond the driver's default. Health with the database stopped
   took about 4 s to answer 500. A proxy that holds connections open could make health slow
   rather than failing.
6. Timestamps now come back with an offset (`+00:00`), as Postgres stores `TIMESTAMP WITH TIME
   ZONE`. This replaces round 1 assumption 10.

### Brief problems (round 2)

- Round 1 items 2 (SQLite and the proxy) and the identity columns are fixed by the regenerated
  brief and schema.
- New: the source's seed only works on a database that checks foreign keys if inserts are
  ordered, because the models have no relationships between `case_audit`/`case_note` and `cases`,
  or between `subcategory` and `category`. I fixed this in the copy's seed. The brief says nothing
  about it, and the source never hit it on SQLite.
- The brief names the engine but no version. I tested with `postgres:17-alpine` only.
- Round 1 item 3 (the brief carries the source digest, not its own) still applies.

## Assumptions

1. **Backend versions**: newest release in each source range (playbook rule), because the source
   pins nothing and nothing in the source says what the real application runs.
2. **Container port 8000** for both web and api, one process.
3. **Which paths serve the page**: `/login`, `/cases`, `/cases/{caseNo}` and `/` serve
   `index.html` (`/` because the source router sends unknown paths on to `/cases`). Every other
   non-API path answers 404, so `/admin/responses` is 404 from the server. The source's client-side
   catch-all route (`*` to `/cases`) is kept, as it is part of the in-scope `main.tsx`.
4. **Creating tables**: at start-up, if none of the seven tables exist, the statements of
   `db/schema.sql` are run unchanged; if all exist, nothing is done; if only some exist, start-up
   stops with an error naming the missing ones. The models are not used to create tables.
5. **Seed**: the source seed is loaded when `app_user` is empty, as in the source, minus canned
   responses. The lab's data packs can replace it.
6. **Default database**: SQLite at `/app/data/showcase.db` inside the container, with no volume, so
   data is lost when the container is removed. Sign-in tokens stay in memory, as in the source.
7. **`API_URL`**: read only by `vite.config.ts` for the Vite dev server's `/api` proxy, as in the
   source. In the container one process serves both, so it has no effect there.
8. **FastAPI's default `/docs`, `/redoc` and `/openapi.json`** are left on, as in the source. They
   list only in-scope routes.
9. **Health failure status**: when the database query fails, health answers 500 (an unhandled
   error), as the source does, not 503.
10. **Timestamps**: SQLite keeps `TIMESTAMP WITH TIME ZONE` as text and gives back times without an
    offset, so `opened_at` and `updated_at` have no `+00:00` in the JSON. The reference on SQLite
    behaves the same.

## Brief problems

1. **Backend versions disagree with the playbook.** The brief says "Pin the version the real
   application runs"; the playbook says to pin the newest version in the range. The source has
   only ranges and no lock, so the brief's instruction cannot be followed from the source. I
   followed the playbook. The host that ran the reference has fastapi 0.141.1, SQLAlchemy 2.0.52 and
   uvicorn 0.35.0 installed, which may be what the real application runs. SQLAlchemy 2.1 and
   Starlette 1.x are newer major/minor lines than that; the reference tests and the checks above
   pass on them, but a reviewer may prefer those older pins.
2. **SQLite and the lab's database proxy do not fit together.** The brief says "the lab agent puts
   a proxy in front of the database to slow it down", and `uipath-case-update` reads `case_audit`
   and `cases` directly (`in_Db`). With SQLite the database is a file inside the container: there
   is nothing to proxy and nothing an outside automation can connect to. `db/schema.sql` is called
   portable, but on PostgreSQL its `INTEGER NOT NULL` keys have no identity, so inserts without an
   id (`app_user`, `case_note`, `case_audit`) would fail. The brief should say how the lab expects to
   reach the database.
3. **The brief's digest is the source's digest.** The pull-request title asks for the brief
   digest; the brief only carries `sha256:3adecca8a37e027b`, which is the digest of the source it
   was read from. I used that.
4. The brief's open questions say none were found; items 1 and 2 above are open questions.
